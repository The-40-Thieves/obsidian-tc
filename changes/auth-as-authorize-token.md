- **The bundled authorization server now issues tokens to statically configured clients.** With `auth.as.enabled`, `/oauth/authorize`, `/oauth/consent` and `/oauth/token` are live, and the discovery metadata, the protected-resource metadata and the 401 challenge now point at them (`/oauth/revoke`, refresh tokens, client metadata documents and dynamic registration are not there yet, and are not advertised). A client listed in `auth.as.clients[]` runs the authorization-code flow with PKCE (`S256` only; `plain` or no challenge is refused) and gets an ES256 RFC 9068 access token signed with the `as` key, bound to the client and to `auth.resource` (`resource` is checked on both legs). The client and the redirect URI are validated before anything can redirect, so a bad one gets a local error page and never a `Location`; loopback redirects match by host and path with the port ignored. Every redirect to a client, errors included, carries `iss`, byte-identical to the metadata issuer. The operator signs in, then a consent page shows the client, its redirect host, the scopes in words (with a loud warning when every redirect is loopback) and a persona and vault picker; the first grant for a client needs a sign-in no older than five minutes, a later request inside a remembered grant skips the page, and a wider one asks again. Consent forms carry a per-request token and need `Origin` equal to the issuer, and every POST answers 303. The account's `scopes_allowed` and `vaults_allowed` are re-read on every decision (consent, remembered consent, token exchange), so narrowing an account takes effect on grants and codes already issued. A code is single-use and lasts 60 seconds; using one twice revokes every token already issued from it, even when the two exchanges race. A confidential static client authenticates with `client_secret_basic` (its secret read from the environment variable named by `secretEnv`); `client_secret_post` and any credentials on a public client are refused. Nothing in `/oauth/*` logs a query string, code, verifier, token, password or cookie. The consent page's Content-Security-Policy names the client's redirect origin in `form-action`, because browsers apply `form-action` to the redirect that answers the POST. See the auth model.

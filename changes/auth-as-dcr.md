- **The bundled authorization server can now register clients by Dynamic Client Registration (RFC 7591), behind `auth.as.dynamicRegistration` (on by default; see the Changed entry).** Claude (claude.ai, Claude Code) and ChatGPT support both Client ID Metadata Documents and DCR and prefer the metadata document, which this server advertises, so they do not need it; it is for clients without metadata-document support (Gemini CLI, Grok Build and Cursor, all unverified). While the flag is on, `POST /oauth/register` takes a JSON registration and answers `201` with a server-chosen `client_id`. Registered clients are public (`token_endpoint_auth_method` must be `none` or absent, so `client_secret_basic`, `client_secret_post` and `private_key_jwt` are refused with `invalid_client_metadata`, and no secret is ever issued), `redirect_uris` must be https or loopback with a private-use scheme such as `cursor://...` dropped rather than refused while one usable URI remains, and `grant_types` and `response_types` must be ones the server serves. The registered `grant_types` are honored and echoed: a client that lists `refresh_token` gets a refresh token, one that lists only `authorization_code` (or nothing, the RFC 7591 default) gets none. A `client_id` in the request is ignored, so a registration cannot take a static client's id or a metadata-document URL; every other member is ignored and never fetched. Registered clients resolve through the same client resolver as static and metadata-document clients, so authorize, consent, token and revocation treat them alike, and their consent page warns that the application registered itself and has never been approved (and, as for any client, nothing is remembered until the operator approves). The surface is bounded: `auth.as.dcr.perIpPerHour` registrations per source (the TCP peer; an IPv6 address counts as its /64; peers behind a same-host proxy or tunnel share one bucket; no forwarded header is read) answer `429` with `Retry-After`, `auth.as.dcr.maxClients` rows answer `503` (a full table first drops registrations never used within a day), and a registration unused for `auth.as.dcr.unusedDays` is deleted by housekeeping. A registration counts as used only when a sign-in succeeds (an authorization code issued or a refresh token rotated), never because its `client_id` was looked up, so unauthenticated probes cannot keep throwaway registrations out of reclamation. One info line is logged at boot while DCR is on, the metadata advertises `registration_endpoint` only then, and `securityProfile: "hardened"` forces DCR off even when the flag is set to `true` (the loader says so). The three `dcr` keys and the flag already existed in the schema and `doctor` output; only the `dynamicRegistration` description changed.

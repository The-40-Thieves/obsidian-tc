- **Passkeys for the bundled authorization server's operator, beside the password, and `obsidian-tc auth as reset-credentials`.** After signing in with the password, `/oauth/account` enrols passkeys (WebAuthn: discoverable credentials, user verification required, attestation `none` only; any other format is refused before it is parsed) and lists and removes them with their last-used time. `/oauth/login` then offers the passkey in the username field's autofill (conditional UI), with a button where autofill is missing, and a passkey login opens the same session a password does; the password keeps working. The relying-party id is the issuer's host and the accepted origin is the issuer's origin, so a credential for another host fails and a change of issuer host orphans the passkeys. The signature counter is stored and a login whose counter is not greater than a stored non-zero one is refused as a possible clone (a constant 0, as synced passkeys report, is accepted); challenges are single-use and live five minutes. The pages now carry `script-src 'self'; connect-src 'self'` for the one script the server serves itself at `/oauth/assets/passkey.js` (no CDN, no inline script); `oauth.db` gains the `webauthn_credentials` and `webauthn_challenges` tables, and `@simplewebauthn/server` 14.0.3 is a new runtime dependency. `obsidian-tc auth as reset-credentials [--user <name>] [--stdin] [--revoke-grants]` recovers a lost passkey and password: it sets a new password, deletes the operator's passkeys and ends every session, and with `--revoke-grants` also revokes every grant with its refresh-token families and live access tokens, all in one transaction. The operator account carries a credential generation (`oauth.db` migration `20261009_954_credential_generation`, `users.credential_gen` and `sessions.credential_gen`) that the reset and `set-password` move on, and every write made on a session's authority (a passkey registration, an enrolment challenge, a consent's grant and code) re-checks inside its own write transaction that the session still exists at the account's generation, so a reset ends operations already in flight rather than being undone by them. `POST /oauth/passkey/login/options` is budgeted per source (a shared bucket for callers behind a loopback proxy), pending challenges are capped per purpose so login challenges cannot take enrolment's room, and failed passkey logins are counted per credential beside the source. See the auth model.

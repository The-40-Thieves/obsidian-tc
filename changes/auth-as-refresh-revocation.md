- **The bundled authorization server now issues refresh tokens, serves RFC 7009 revocation, and has `auth as grants list|revoke`.** Every authorization-code exchange returns a `refresh_token` (whether or not `offline_access` was asked), and `refresh_token` is advertised in `grant_types_supported` with `offline_access` in `scopes_supported`, together with `revocation_endpoint`, because `/oauth/revoke` is now mounted. Only a SHA-256 of a refresh token is stored. Tokens rotate on every use and the family dies `auth.as.refreshTokenDays` after the exchange that started it (rotation never extends it). A client that lost a refresh response can retry the previous token until its successor is used, and is handed the same response again, the same access token and the same successor (so two simultaneous refreshes never fork the family, and one stolen token cannot be turned into any number of bearers; the stored copy is sealed under a key derived from the server secret). A refresh token belongs to the server secret that minted it: replacing the secret retires every family (the next use is `invalid_grant` and revokes it, and a family from before this release signs in once more). Revoking a family or a grant is queued durably in `oauth.db` in the same transaction and then paid into the registry, so a busy or full `auth.db` cannot leave a revoked family's access tokens live. Presenting any older token, or the previous one after its successor was used, revokes the whole family: the refresh token and every access token issued from it stop working at `/mcp`. Only a presentation by the token's own client can do that; another client, an unknown token or a revoked grant is refused and changes nothing. Every refresh failure is the same `invalid_grant`. The account's `scopes_allowed` and `vaults_allowed` are re-applied at each refresh (a narrowed account gets a narrower access token, an emptied one is refused), and a refresh may narrow `scope` but never widen it. `POST /oauth/revoke` authenticates the client like the token endpoint, revokes a refresh token's family or an access token's `jti`, and answers an empty 200 for anything it cannot act on, another client's token included. `obsidian-tc auth as grants list [--all]` shows the grants and their live refresh families, and `auth as grants revoke <id>` kills a grant's refresh tokens and every live access token issued under it. See the auth model.

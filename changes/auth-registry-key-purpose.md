- **Signing keys now have a purpose, so a second key can be active without retiring your first.** Every registry key is `mint` (the tokens `obsidian-tc token mint` prints, and the write-provenance chain) or `as` (access tokens for a bundled authorization server, which a later release adds), with one active key per purpose. A new `auth.db` migration adds `auth_keys.purpose` (existing rows become `mint`) and makes the active-key index per purpose, so a deployment that never creates an `as` key behaves exactly as before, and the hand-minted HS256 flow is byte-identical. `obsidian-tc auth rotate-key --purpose as [--alg ES256|EdDSA] [--grace N]` rotates the `as` key on its own (HS256 is refused for it); replacing an `as` key needs a grace window of at least the access-token lifetime plus 60 s (1860 s by default, also the default when `--grace` is omitted). `auth list --keys` shows each key's purpose and `/.well-known/jwks.json` publishes the asymmetric keys of both purposes. A token whose `kid` names an `as` key is held to rules of its own, chosen by the key's purpose and not by anything the token claims: `iss` equal to the authorization server's issuer, `typ: at+jwt`, `client_id`, `aud` equal to `auth.resource`, and `jti`; a stray `scopes` array is ignored. For those tokens only, a persona's effective scopes are the persona's scopes intersected with the token's `scope` (removal only); a hand-minted persona token still has the persona's scopes replace its own. Losing one purpose's keys fails closed on its own marker (`.as-keys-initialized`) without reviving the configured secret, and token records a day past `exp` are now deleted at server start and by the maintenance sweep (the newest record and revocation tombstones stay). Nothing signs with an `as` key yet, and the verifier refuses every `as` token until the authorization server's issuer is configured, so creating one enables nothing by itself. See "Key purposes" in the auth model.

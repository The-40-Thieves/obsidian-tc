- **A Claude Code plugin, a Muse Code plugin, and generated one-click install links.** The repository is now a Claude-style plugin marketplace: `claude plugin marketplace add The-40-Thieves/obsidian-tc`, then `claude plugin install obsidian-tc@the-40-thieves`. The plugin (`plugins/obsidian-tc`) launches the published package over stdio, pinned to its own version (`npx -y obsidian-tc@<version>`), and asks for the config file path when enabled. A `.muse-plugin/plugin.json` carries the same server for Muse Code; its format follows existing Muse plugins and has not been checked against Meta documentation, which does not describe it. `check:version` and the release script now keep both manifests and both launcher pins in lockstep with the package version. The Cursor and VS Code (and VS Code Insiders) install links in the README and install page are generated from `server.json` by `scripts/gen-install-links.mjs`, and CI fails if they drift; a test decodes each link and compares it with the launch config. `docs/DISTRIBUTION.md` lists every directory, what it needs and its status. Nothing was submitted anywhere.
- **`call_capability` states all three tool annotations.** It carried only `openWorldHint`; it now also states `readOnlyHint: false` and `destructiveHint: true` (it can reach any tool). A new test lists tools through a real server for the core surface and every facade mode and fails on any tool that leaves `readOnlyHint`, `destructiveHint` or `openWorldHint` unstated, which directory reviews require. `server.json` is now validated against a vendored copy of the MCP Registry schema.
- **`docs/MCP-COMPATIBILITY.md` cited stale SDK versions** (1.29.0 and 2.0.0; the lockfile resolves 1.32.1 and 2.3.1). It now matches, and `docgen:facts-check` compares every SDK version in prose with `bun.lock`, so it cannot drift again.

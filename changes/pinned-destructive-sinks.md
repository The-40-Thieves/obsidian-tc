- **Permanent deletes and the write batch's rollback no longer act on a retargeted symlinked wiki or raw folder, and a symlinked configured folder is refused on the pure-JS path.** With `wiki -> open` configured, the ACL could approve `wiki/x.md` and the symlink be retargeted to the immutable `raw/` before the I/O: `hardDelete` (behind `delete_note`/`delete_attachment` with `permanent`, and the memory and periodic deletes) called `rmSync` on the live alias and removed `raw/x.md`, and the write batch's move-aside, drop and rollback steps (`move_note`, `bulk_move_notes`, `move_attachment`, `commit_wiki_page`) used raw `renameSync`/`unlinkSync`/`rmdirSync` on it, so a rollback could take or fail to restore a file in the wrong folder. The native module now has `safeUnlink(abs, pinned?)`, which opens the parent with `O_NOFOLLOW`, verifies the pinned directory's identity and unlinks on that directory, and every one of those steps goes through it (or the already-pinned no-replace move) instead of the lexical path. An addon that predates `safeUnlink` refuses a delete through a pinned folder instead of falling back to `rmSync`. Separately, the pure-JS path (Windows, `OBSIDIAN_TC_FORCE_JS_FALLBACK=1`, an install without the addon) can only open a pinned directory by path, leaving a window between the identity check and the open, so it now refuses every read, write, move and delete of a path that runs through a configured symlinked folder with `acl_denied` ("configured symlinked folders require the native module"). **Behaviour change:** on those platforms a `wiki.folder` or `wiki.rawFolder` that is a symlink is no longer served; folders that are not symlinks, and everything else, work as before. Documented in `SECURITY.md`, the configuration reference and the compatibility page.
- **A pinned folder is pinned under its real directory's own name too, and the scheduled jobs that delete or write in a vault run under the pins.** With `wiki -> open` configured, a caller who named the target directly (`open/x.md`) reached the destructive and batch sinks with no pin, so renaming `open` away and `raw` into its place after the ACL decision made a permanent delete, a move or a write batch's removal or rollback act on the replacement. A path beneath a pinned directory now keeps its spelling and gets the same pin as the alias spelling (the ACL's verdict and every sink, including the pure-JS refusal), and `noteExists`/`statNote` no longer stat a pinned folder through the live alias (refused on the pure-JS path; with the native module they check the pinned directory's identity and stat its own name). Separately, the default-enabled trace-retention sweep resolved a legacy `workspace.traceFolder` beneath such a folder once, at boot, and then enumerated and `rmSync`'d the lexical `wiki/...` path outside any pin: a persistent retarget made it delete an aged same-named `.jsonl` in the replacement directory (inside the immutable `raw/` or outside the vault). The sweep now runs under the vault registry's folder pins, re-checks the folder against the ACL on every run, enumerates the pinned name, and deletes through the same pinned unlink, skipping the folder with a warning when it no longer matches; the scheduled wiki-page regeneration runs under the pins as well. **Behaviour change:** on the pure-JS path the directory's own name (`pages/x.md`) of a symlinked configured folder is now refused like the configured one (`wiki/x.md`). Documented in `SECURITY.md`, the configuration reference and the compatibility page.

- **A remembered consent no longer issues an authorization code on a bare `GET /oauth/consent` for a redirect that leaves this machine.** Before, a signed-in operator who opened one crafted authorize link for a client they had approved before was sent straight to that client's redirect with a fresh code, with no click and no CSRF token. Now such a sign-in shows a one-click Continue page, and the code is issued only by its same-origin, token-bound POST. The new `auth.as.consent.remembered` key (`silent | confirm`) controls this. Unset, it is `silent` for a redirect on this machine (`127.0.0.0/8`, `::1`, `localhost`), which is remembered only under `auth.as.consent.loopback: remember`, and `confirm` for any other redirect. Set `silent` to restore the old behaviour everywhere, or `confirm` to show the Continue page for loopback sign-ins too. Refs #1472.
- **A sign-in request that can no longer be used now says why.** The consent page used to answer "expired or was already used" for four different cases. It now tells apart a damaged or cut-short link, a request this server has no record of, a request past its 10-minute limit, and one already completed or cancelled, and it logs `consent refused reason=<malformed|unknown|expired|used>`. A consumed request is kept as a tombstone for 10 minutes past its expiry instead of being deleted at once (new oauth.db migration `20261108_956_auth_requests_used.sql` adds `auth_requests.used_at`); tombstones do not count against the admission limits. Refs #1478.

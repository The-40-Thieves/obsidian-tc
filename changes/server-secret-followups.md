- **Server-secret hardening.** Processes that start together on a corrupt `<cacheDir>/server-secrets/wiki-generated.key` now repair it under a lock and all adopt the one regenerated key, even when a repairer stalls (the repair lock is taken over only from a holder that is provably dead on the same host, never because time passed, so a slow or stopped repairer cannot split the key; a live holder, another host or an unreadable owner makes the start fail after 15 s with an error naming the lock to delete, and a lock directory's owner can no longer be overwritten or retried without bound; a valid key is never replaced) (before, each returned its own and only the last survived in the file, so confirmations minted by the others failed to verify). A key the server refuses for being readable by group or other now says to delete it rather than hint at tightening the mode: such a key must be treated as disclosed, and there is no rotate command, so the operator deletes the file (pending confirmations are refused once and generated wiki pages regenerate). Startup logs an `elicit:` line saying whether the HITL codec uses the stable file key or a per-process random key (no `cacheDir`). The docs now cover `auth.mode: none` on loopback, the replay window under `oidc`, asymmetric-only `jwt` and a shared `cacheDir`, manual rotation, and keeping `server-secrets/` on the same persistent volume as `auth-keys/`.

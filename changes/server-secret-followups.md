- **Server-secret hardening.** Processes that start together on a corrupt `<cacheDir>/server-secrets/wiki-generated.key` now repair it under a lock and all adopt the one regenerated key, even when a repairer stalls past the lock's stale threshold (the lock is fenced with an owner token and a valid key is never replaced; a lock that cannot be cleared fails with an error naming it after 15 s instead of spinning) (before, each returned its own and only the last survived in the file, so confirmations minted by the others failed to verify). A key the server refuses for being readable by group or other now says to delete it rather than hint at tightening the mode: such a key must be treated as disclosed, and there is no rotate command, so the operator deletes the file (pending confirmations are refused once and generated wiki pages regenerate). Startup logs an `elicit:` line saying whether the HITL codec uses the stable file key or a per-process random key (no `cacheDir`). The docs now cover `auth.mode: none` on loopback, the replay window under `oidc`, asymmetric-only `jwt` and a shared `cacheDir`, manual rotation, and keeping `server-secrets/` on the same persistent volume as `auth-keys/`.

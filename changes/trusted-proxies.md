- **`transports.http.trustedProxies` and `transports.http.forwardedHeader` attribute clients behind a reverse proxy or Cloudflare Tunnel by their real address.** The per-source limits (client-metadata-document lookups, passkey sign-in, dynamic registration, `/oauth/authorize` admission, failed-login counting) key on the client address, which was always the TCP peer: behind cloudflared on the same host every client was the loopback peer, so one caller could use up the shared allowance (10 metadata-document lookups a minute, 60 passkey challenges a minute) for everybody. List the proxies' addresses or CIDR blocks in `trustedProxies` (default empty: nothing changes) and the address comes from the header `forwardedHeader` names: `x-forwarded-for` (default; the right-most hop that is not itself a trusted proxy) or `cf-connecting-ip` (Cloudflare). The header is read only when the connecting peer is listed; from any other peer it is ignored, and a header that cannot be parsed falls back to the peer, never to a guess. IPv4-mapped IPv6 peers match IPv4 entries, an IPv6 client is counted as its /64 by every one of those limiters, and a `/0` prefix, an IPv6-form block spanning all IPv4 addresses, a hostname or a wildcard is refused at load. All of those limiters share one resolver (`auth/client-ip.ts`), so none keeps the raw peer. For a Cloudflare Tunnel on the same host set `trustedProxies: ["127.0.0.1", "::1"]` and `forwardedHeader: cf-connecting-ip`; never list a proxy you do not control. See "Running behind a proxy or tunnel" in the auth model.

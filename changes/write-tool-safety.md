- **Write tools are safer against hostile names, planted symlinks and create races.** A write that would create a name Windows treats specially (a `:` in a segment, such as `report.md:.png`, which names an NTFS alternate data stream; a trailing dot or space; a reserved device name like `CON` or `NUL`) is now refused on every platform, while files that already exist under such a name stay readable and updatable in place. The soft-delete to `.trash` and the rollback after a failed overwrite no longer follow a planted `.trash` symlink, and parent directories are created one component at a time, refusing any symlinked component. `overwrite: false` (and every create-only writer) now commits with an exclusive no-replace rename, so a file created by another process between the check and the write is never replaced. `write_attachment` marks its effect committed only after the write succeeds (or cannot be rolled back), its ACL extractor fails closed without a vault root, and its protected-directory check uses the resolved path. `bulk_move_notes` reports only backlinks in notes the caller may read (plus `hidden_backlinks: true` when others exist); the vault-wide link rewrite is unchanged Overwrites (`move_note`, `copy_note`, `move_attachment`, `bulk_move_notes`, `write_attachment`) share one replace step: every refusal (including the memory-defense scan) runs before the destination is moved to `.trash`, a failed write puts the destination back exactly where it was, and an existing name such as `a:b.md` is replaced in place instead of being stranded in `.trash`. Where hard links are unavailable the pure-JS move copies with an exclusive create instead of renaming over the target, `find_or_create_periodic_note` and `append_to_periodic_note` create exclusively (a lost race returns, or appends to, the note that won), and the native no-replace rename removes the destination link again when the source cannot be unlinked (#1058).

# Security Model (G2.4)

obsidian-tc treats its security surface as a first-class deliverable. This document specifies the authentication model, authorization model, runtime governance, and refusal taxonomy. Every dangerous capability is either gated by explicit operator opt-in or fenced by a hardcoded floor that vault configuration cannot override.

## Threat model

**Targets to protect:** vault content (notes, attachments), agent-managed memory (memory_entities, capture queue), operator credentials, and the host system where obsidian-tc runs.

**Attackers in scope:**

- Compromised caller (stolen JWT, malicious agent with valid token).
- Malicious vault content (a note that tries to elicit, capture data via plugin bridges, or escape via templates).
- Plugin-level RCE (Templater run, QuickAdd, Smart Connections proxying caller input into arbitrary code).
- Network attacker on a non-localhost deployment.

**Out of scope (V1):**

- Adversarial Obsidian itself (we trust the Obsidian process and its Local REST API plugin).
- Adversarial filesystem (we trust OS path resolution).
- Adversarial npm/cargo registry (we trust transitively reviewed dependencies).

## Authentication

### Transport posture

Two transport modes. STDIO for local single-user use. Streamable HTTP for remote agents.

Auth modes:

- `none`: no auth. **Hardcoded refusal** to bind non-localhost addresses with this mode (G2.2 commitment 8). Source-code-level refusal, not config-overridable.
- `jwt`: required for any non-localhost deployment. The default for HTTP transport.
- `oidc`: bring-your-own OpenID Connect provider. The server verifies access tokens an external identity provider issues; it does not issue, refresh or register anything (verification only, no authorization server). See [OIDC mode](#oidc-mode) below.

### OIDC mode

`auth.mode: "oidc"` with an `auth.oidc` block verifies bearer tokens from an external OpenID Connect provider. Nothing about the HS256 path changes, and none of it is available under another mode: an `auth.oidc` block beside `mode: none` or `jwt` is refused at config load, because it would look like protection while none applied.

Trust chain. The operator configures an https `issuer` and a required `audience`. At boot the server fetches `<issuer>/.well-known/openid-configuration` (https only, no redirects, 5 s timeout, 64 KiB cap) and accepts the document only if its `issuer` equals the configured one **exactly** (the mix-up defence). Its `jwks_uri` (https, no credentials in the URL, on the issuer's origin or a host in `auth.oidc.allowedJwksHosts`, or the `auth.oidc.jwksUri` override) feeds jose's remote key set (256 KiB cap, refetch on an unknown `kid` at most once per 30 s). If discovery fails the server **does not start** (the error names the issuer), `doctor` reports `auth.oidc` as FAIL with the same probe, and a successful boot logs the issuer, `jwks_uri`, audience and algorithms. The discovery document is trusted for `auth.oidc.discoveryCacheSeconds` (default 3600, 60 to 86400); a refresh that fails or returns another issuer refuses tokens, never a stale document. Every provider fetch first resolves the host and is refused if any address is loopback, link-local (cloud metadata), private or reserved, unless `auth.oidc.allowPrivateNetwork` is true (a LAN identity provider); the resolve-then-fetch check cannot pin the connection, so a DNS answer that changes in between is not covered.

| Check | Rule |
| --- | --- |
| Signature | Key from the IdP's JWKS, selected by `kid` |
| Algorithm | Must be in `auth.oidc.allowedAlgs` (default RS256, ES256, EdDSA), checked from configuration, never from the header alone. Only asymmetric algorithms are expressible: `HS256/384/512` and `none` are rejected at config load, and an HS256 token signed with the IdP's public key as its secret is refused (`unsupported_alg`) |
| `iss` | Exactly `auth.oidc.issuer` (no normalisation; a trailing slash differs) |
| `aud` | Contains `auth.oidc.audience` (a string, or any one of a list) |
| `exp`, `nbf`, `iat` | `exp` and `iat` required; `exp`/`nbf` checked with `clockToleranceSeconds` (default 30, maximum 300); an `iat` in the future beyond the tolerance is refused; `auth.tokenTtlSeconds` caps age from `iat` as in jwt mode |
| `typ` (RFC 9068) | `at+jwt` and `application/at+jwt` always pass. Default: `JWT`, `Bearer` and an absent `typ` also pass, because Entra and Keycloak put `JWT` there; any other header `typ` (for example `id_token+jwt`), or one that is not a string, is refused. `requireAtJwtType: true` demands `at+jwt` strictly |
| Token kind (payload) | The header cannot tell an ID token from an access token, so the payload is read too: a `typ` other than `Bearer`/`Access` (Keycloak `ID`, `Refresh`), a `nonce`, `at_hash` or `c_hash` claim, or a Cognito `token_use` other than `access` is refused (`invalid_token_type`) |
| Client | With `clientId` set, the token's `client_id` or `azp` must equal it |
| Claims | The subject claim is required. `requiredClaims`: a list of names each needs a truthy, non-empty value (`email_verified: false` fails); an object of `name: value` needs that exact value |
| Revocation | `jti` checked against the auth registry after everything above verified; `obsidian-tc auth revoke <jti>` writes a tombstone for a token this server never minted. `auth.requireJti` applies, and a lost or partly lost registry refuses every token, jti or not (`registry_lost`), in oidc and jwt mode alike |

Identity. The verified claims become the same identity jwt mode produces (caller, scopes, optional vault, optional persona), so folder ACL, rule-scopes, vault binding and personas apply unchanged. `claimMapping` names the claims: `subject` (default `sub`), `scopes` (default `scope`; `scp`, or a path such as `realm_access.roles`; a space-delimited string or an array), and optionally `principal` (the caller label used in audit, for example `email`), `vault` and `persona`. A string names a claim or a dotted path into NESTED objects only, so a forged top-level `realm_access.roles` never shadows the nested claim; a claim whose own name contains dots (`https://app.example.com/roles`) is written as an array of literal segments. Only the mapped claim grants scopes, and only fully-qualified values (`read:notes`, `write:*`) pass: a bare value such as the role `admin` would be read as the wildcard `admin:*`, so it is dropped (logged once) unless `claimMapping.scopeMap` maps it (`{ "vault-reader": ["read:notes"] }`). `vault` and `persona` are bearer capabilities: each is read only when mapped, needs `allowedVaults` / `allowedPersonas`, and a token naming anything outside them is refused (`claim_not_allowed`).

Discovery to clients. With `auth.resource` set, the Protected Resource Metadata document (RFC 9728) advertises the configured issuer as its `authorization_servers` entry and a `401` carries `WWW-Authenticate: Bearer resource_metadata="..."`. The document carries `resource`, `authorization_servers`, `bearer_methods_supported: ["header"]` and, when configured, `scopes_supported` and `resource_name`. `auth.authorizationServers`, if also set, must be exactly the issuer. The same verifier guards `/metrics` on a non-loopback bind.

Not in scope: obsidian-tc does not register clients, run an authorization or token endpoint, or issue refresh tokens here. Whether a given MCP client can obtain a token from your IdP (dynamic registration, client metadata documents, redirect URIs) is the IdP's concern. The bundled authorization server is a separate design with its own config namespace, which this block does not use.

### Token issuance

JWTs are minted by the operator via CLI:

```bash
obsidian-tc token mint ./config.json \
  --sub "agent-claude-2026-05-19" \
  --vault personal-vault \
  --scopes 'read:* write:notes write:meta bulk:*' \
  --ttl 7d
```

Every minted token gets a `jti` claim and a `kid` header, and is recorded in the issued-token registry (see [Revocation](#revocation)) before it is printed.

The CLI emits the token to stdout. The operator delivers it to the caller out-of-band. Server self-issuing is not supported in V1; a server `/auth/issue` admin endpoint would make any compromised admin token a total-compromise pivot.

### Token shape

```jsonc
{
  "iss": "<vault_id>",
  "sub": "<caller_id>",
  "aud": "obsidian-tc",
  "vault_id": "<vault_id>",
  "scopes": ["read:notes", "write:notes", "bulk:*"],
  "iat": 1758268800,
  "exp": 1758873600,
  "jti": "<uuid>"
}
```

Signing: HMAC-SHA-256 (HS256). The initial signing key is the configured `auth.jwtSecret` (or `OBSIDIAN_TC_JWT_SECRET`), registered under the reserved `kid` `config`; a deployment that never rotates behaves exactly as before the registry existed. Keys added by `auth rotate-key` are stored as `<cacheDir>/auth-keys/<kid>.key`, mode 0600 in a real 0700 directory. Trust is judged on the open descriptor (`O_NOFOLLOW` open, then `fstat`: regular file, owned by the server user, no group/other bits; a symlinked file or directory is refused) and re-checked at least once a second (a validated secret is reused for at most one second, which is the longest a later `chmod` or symlink swap can go unnoticed); keys are created `O_EXCL|O_NOFOLLOW`. Windows has no POSIX modes, owner check or `O_NOFOLLOW`, so none of this is enforced there (`doctor` warns; use the directory ACL). Key material is never stored in `<cacheDir>/auth.db`; the `auth_keys` table holds only the `kid`, a reference to where the secret lives, and the key's state.

### Key rotation

```bash
obsidian-tc auth rotate-key [--grace <seconds>] [--alg HS256|ES256|EdDSA] [config-path]
```

Generates a new signing key and makes it the only `active` one. The previous key becomes `retiring` with `retire_after = now + grace`, and stops verifying at that instant; with the default `--grace 0` it is retired immediately and every token it signed stops verifying, so the operator reissues tokens to callers. With `--grace N` the old and new keys both verify for `N` seconds, so callers can move over without an outage.

Without `--grace` the window is `auth.rotationGraceSeconds` (default 0, maximum 604800 = 7 days); an explicit `--grace`, including `0`, wins. The window is exact: the verifier compares `retire_after` on every request, and the reaper that persists `retiring` to `retired` (on `rotate-key`, on server start and in the periodic maintenance sweep) is housekeeping that verification never waits for. `obsidian-tc doctor` lists each retiring key with its time remaining and warns on a window with more than a day left; `obsidian_tc_auth_keys{state}` is the gauge. `token mint --kid <kid>` pins a mint to the ACTIVE key and refuses a retiring, retired or unknown one.

`--alg ES256|EdDSA` creates an asymmetric key: the private JWK lives in the 0600 key file (same `O_NOFOLLOW`/`fstat` trust path), `auth_keys.public_jwk` holds the public half, and `GET /.well-known/jwks.json` publishes the active and in-window retiring public keys (public members only) so other verifiers can validate. Its `Cache-Control: max-age` is 60 s capped at the seconds left until the earliest `retire_after` among the published keys (`no-cache` when under a second), with an `ETag` over the key set and `304` on a match, so a cache that honours it never serves a retiring key past the moment this server stops verifying it; a retirement made after the cache fetched (`--grace 0`) is not covered and can linger up to 60 s. The algorithm comes from the registry row, never from the token header alone: an HS256 header naming an asymmetric key, an asymmetric header naming an HS256 key, a mismatched asymmetric algorithm and `alg: none` are all refused (`unsupported_alg`). Once the `config` key is retired, `auth.jwtSecret` may be removed: verification and minting run from registry keys alone (a `jwt` server with no secret, no JWKS and no registry key refuses to start).

Keys are looked up by the token's `kid` header, and more than one may be valid at once. The state machine is `active` to `retiring` to `retired`; a `retiring` key is accepted only while `now < retire_after`, whether or not its row has been rewritten to `retired` yet. Tokens minted before the registry existed carry no `kid` and verify against the `config` key, so they follow that key's state. Tokens naming a `kid` the registry does not hold are refused (`unknown_key`) once any rotation has happened.

The `auth_keys` and `auth_tokens` tables live in their own file, `<cacheDir>/auth.db` (with the key files in `<cacheDir>/auth-keys/`), NOT in `cache.db`. They hold operator decisions (a revocation, the key list) that cannot be regenerated, so unlike `cache.db` they must be backed up; `rm cache.db*`, `compact`, `reset_vault_cache` and the maintenance sweep never touch them. The server fails closed on loss, judged per table from two durable markers in `auth-keys/`, outside the database: `.keys-initialized` (first key rotation; any `*.key` file also counts) and `.tokens-initialized` (first recorded token or revocation). A table whose marker exists but which now holds no rows, or a `<cacheDir>/auth.db` that is missing, makes the verifier refuse every HS256 bearer with reason `registry_lost` (startup log, `doctor` and the CLI name the recovery: restore `<cacheDir>/auth.db` from backup) instead of falling back to `auth.jwtSecret` and reviving retired keys and revoked tokens; an emptied `auth_keys` beside surviving tokens, or an emptied `auth_tokens` beside surviving keys, is refused the same way. A marker is created inside the transaction of the first write it protects and is never removed unless nothing else committed under it, so no committed row exists without its marker. An `auth-keys/` that is a symlink (even to an empty directory) or not a directory is refused as lost and reported by `doctor`. Only a table that was never initialised keeps the legacy reading (no keys: the configured secret verifies; no tokens: nothing is revoked). The one way back to that state is destructive and intended: remove BOTH `<cacheDir>/auth.db` and `<cacheDir>/auth-keys/` (the markers live in it), which un-retires every key and un-revokes every token.

### Revocation

```bash
obsidian-tc auth revoke <jti> [--reason <text>] [config-path]
```

Marks one issued token revoked before its `exp`. The verifier looks the `jti` up in the `auth_tokens` table on every request, after the signature has verified, on the HS256 and the JWKS paths and on the `/metrics` scrape alike. There is no in-process cache, so a revocation written by one process is seen by every other process sharing the same `<cacheDir>/auth.db` on its next request. A rejected token is logged and counted as `token_revoked`; the caller sees the same undifferentiated `401` as for any other bad token.

`auth revoke` on a jti this registry never issued writes a tombstone (jti, `revoked_at`, reason; kid, sub and expiry NULL), so a token minted before the registry existed, or by an external JWKS issuer, is refused as soon as it carries that jti. Limits: a token with NO `jti` cannot be revoked individually; only rotating its signing key kills it. Set `auth.requireJti: true` to reject jti-less tokens on every path, `/metrics` included. `securityProfile: "hardened"` sets it `true` (an explicit `false` wins). The default stays `false` for compatibility and is planned to flip to `true` at the next major release; `doctor` recommends `true` once the registry is initialised. `/metrics` also binds the same audience and issuer as the HTTP edge. A task already enqueued keeps the scopes it was enqueued with (see `mcp/tasks.ts`): revocation is checked when a request is authenticated, and a queued task has no request, so revocation stops the next request, not work already queued or running (the payload carries no `jti` to re-check when the task starts; not done, deliberately).

## Authorization

Authorization runs in ACL layer L3 of the dispatch pipeline (located by G2.2 commitment 2). Three checks in order: scope check, bulk-class check, path check.

Verb-family × domain-bucket. Flat snake_case strings. About 30 scopes total.

Hierarchy: family wildcard (`read:*`, `write:*`, `admin:*`, `execute:*`) satisfies any scope in that family. Sibling scopes do not imply each other.

### Folder ACL

Glob patterns, last-match-wins. Default ruleset:

```yaml
folder_acl:
  defaults:
    - allow: "**"
    - deny: ".obsidian/**"
    - deny: ".trash/**"
    - deny: ".git/**"
    - deny: "**/_archive*/**"
  per_scope:
    write:templater:
      - deny: "**"           # opt-in only; operator must add explicit allows
    write:notes:
      - inherits: defaults
    read:notes:
      - inherits: defaults
```

Path resolution: the folder ACL gates the **symlink-canonical** (realpath-resolved) vault-relative path per request, plus an **inode guard** — a hard-linked regular file (`st_nlink > 1`) is rejected under an ACL (a hard link aliases an inode realpath cannot dereference), reads run on the opened fd, and the atomic write opens its temp file `O_EXCL | O_NOFOLLOW` on a random name (v1.3.2), and the .obsidian/.git/.trash default-deny folds case so a case-variant control-directory path cannot evade it on a case-insensitive filesystem (v1.3.3). config paths use `realpath` at startup per G2.2. Refusal: `path_denied` with `details: { path, scope, rule_id }`.

**Ancestors vs. inside the vault (THE-1081):** an ancestor directory of an EXISTING configured vault root is canonicalized through realpath once, at registration, and may safely be a symlink (e.g. macOS `$TMPDIR` under `/var` -> `/private/var`), on both backends. A symlink anywhere below the root is refused on both backends regardless: the native addon's per-component `O_NOFOLLOW` walk (`open_parent`, THE-272), and this same realpath-containment check on the JS side. A root that does not exist yet at boot is registered by its lexical path and is refused later, on both backends, if it turns out to be a symlink itself.

### Scope evaluation order

1. Validate JWT signature and expiry (Transport L2).
2. Resolve required scopes for tool from G2.1 spec.
3. Check each required scope against token scopes with hierarchy expansion.
4. Check `bulk:*` if tool is a bulk variant.
5. Resolve all paths in args via canonical path rules.
6. Run folder ACL per path against scope-specific rules.
7. On pass: dispatch to Policy layer L4c for HITL evaluation.

Refusal taxonomy:

- `scope_denied`: token lacks required scope.
- `bulk_scope_required`: tool is bulk variant; token has underlying scope but lacks `bulk:*`.
- `path_denied`: folder ACL rejected one or more paths.

## HITL governance

The elicit primitive (G2.2 commitment 5) is the human-in-the-loop checkpoint for actions that warrant operator confirmation. Tokens are minted by Policy layer L4c, returned via MCP elicitation, and consumed on the caller's confirmation call.

### Elicit token lifecycle

| Attribute | Value                                                          |
| --------- | -------------------------------------------------------------- |
| Format    | 16 bytes random, hex-encoded (32 chars). `crypto.randomBytes`. |
| TTL       | 5 minutes (G2.2 bonus).                                        |
| Use       | Single-use. First-consume-wins-redemption.                     |
| Binding   | Bound to `(vault, tool_name, args_hash, caller)` (G2.3 D1; caller binding v1.3.2).                   |
| Storage   | `elicit_tokens` table per G2.3 D1.                             |
| Sweep     | 60s fast-sweep via `setInterval` (G2.3 D9).                    |

### Thresholds and floors

Tool-level HITL class declared in G2.1 spec is the floor. Vault config may raise (more cautious) but not lower below the floor for high-risk scopes.

Hardcoded floors (cannot be lowered):

| Pattern                  | Floor             |
| ------------------------ | ----------------- |
| `execute:*` family       | `always_elicit`   |
| `bulk_delete_*` tools    | `always_elicit`   |
| `admin:auth` scope       | `always_elicit`   |
| `write:templater` scope  | `always_elicit`   |

Vault config:

```yaml
hitl_thresholds:
  bulk_delete_notes: { mode: always_elicit }       # cannot lower
  bulk_create_notes: { mode: threshold, gt: 50 }   # raised from spec default
  read_note: { mode: never }                       # ok to lower; read is non-destructive
```

Refusal-to-lower at server startup: `hitl_floor_violation` error naming the scope and the floor value.

## Runtime governance

### Response-byte governor

Single byte cap shared with idempotency cache (G2.3 D2). Default `1048576` (1 MB). Per-tool override supported.

Behavior by tool class:

| Class                                  | Behavior                                                                                           |
| -------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Pagination-aware (search, list, query) | Refuse with `response_too_large`; `details` includes `suggested_limit` and `current_bytes_estimate`. |
| Read-single (`read_note`, `get_attachment`) | Truncate output; response includes `truncated: true` and `overflow_bytes: <N>`.               |
| Bulk variants                          | Refuse if total > cap; `details` suggests smaller batch.                                           |

Idempotency replays return the same truncated result with the same `overflow_bytes` flag — replay is deterministic across the governor. The `result_size` column on `idempotency_keys` (G2.3 D2) is the pre-truncation size; the governor reads it for replay sizing.

Config:

```yaml
response_governor:
  max_bytes: 1048576              # default; matches idempotency.max_result_bytes
  per_tool:
    read_note: 5242880            # 5 MB override
    get_attachment: 10485760      # 10 MB override
```

### Idempotency error taxonomy

Errors (call rejected):

| Code                        | Cause                                                                         |
| --------------------------- | ----------------------------------------------------------------------------- |
| `idempotency_key_mismatch`  | Same key, different `args_hash`. Hint: stored `args_hash[:8]`.                |
| `idempotency_in_flight`     | Same key currently executing in another caller. Caller should retry.          |

States (logged, behavior = forward to fresh execution):

| Code                          | Cause                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------ |
| `idempotency_cache_skipped`   | Original result exceeded `max_result_bytes`; cache was never written.          |
| `idempotency_key_expired`     | Key TTL elapsed (default 24h, G2.3 D2/D5).                                     |

In-flight detection: `idempotency_keys.started_at` and `completed_at` columns. Row with `started_at IS NOT NULL AND completed_at IS NULL` is in-flight. `result` and `result_size` are nullable (NULL while in-flight, populated on completion). Lock TTL 60s; rows reaped by the existing 60s fast-sweep (G2.3 D9).

Idempotency replays stay best-effort: callers should not rely on referenced state (note IDs, attachment paths, etc.) being live at replay time.

HITL confirmations are stricter. A confirmation approves the state of the target as it was when the request was raised, so redemption is refused when that state has since changed:

| Code           | Cause                                                                                                                                    |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `replay_drift` | An elicit token or `requestState` was redeemed after the call's target paths changed (content, mtime, size, inode, or created/removed). Not retryable; re-issue the call with no token to request a fresh confirmation. |

The fingerprint covers what the tool says its confirmation is about: the vault paths it declares in `pathAcl`, and/or the state its `confirmationTargets` function computes (`rewrite_link`: the notes it would rewrite; `ocr_bulk`: the attachments it would read; `git_commit`: HEAD and the staged index; `reset_vault_cache`: the rows and embedding generations it would clear; `delete_entity`: the entity row, relations and note; `session_rerun`: the session row and, once ended, its trace). A missing path is a state, so a note created after the request is drift too. It is taken when `elicit_required` is raised (recorded per vault, `args_hash` and caller, and returned as `details.state_fp`), copied onto a token when it is minted (including by `obsidian-tc elicit`) or into the signed `requestState`, and recomputed at redemption. A drifted token is spent, nothing is applied, and the caller gets `replay_drift` rather than `elicit_required`. `execute_command` and `trigger_quickadd` declare `confirmationTargets: "none"` (their effects are opaque Obsidian state) and redeem on `args_hash` alone. Registering a HITL-gated tool with neither `pathAcl` nor `confirmationTargets` throws at startup. `obsidian-tc elicit` cannot rebuild a call's arguments from an `args_hash`, so it refuses to mint unless the server actually raised a request for that hash; a token issued directly through `issueElicitToken` with no raised request stays unbound.

### `show_file_in_obsidian` governance

`show_file_in_obsidian` opens an existing note in the Obsidian app, so it causes a host-side effect and follows `execute_command`'s gating: scope `execute:uri` (the execute family is a HITL floor, so dispatch demands a human token) and the execute-tier rate limit. It declares `pathAcl` (op `read`), so the read ACL is enforced centrally before the handler and the confirmation binds to the note's state; the handler re-checks the ACL and that the note exists.

Two launch paths, tried in order. (1) The companion plugin's `POST /files/open` opens the file in the live Obsidian session. (2) The OS URI handler runs only when `uri.allowOsLaunch` is `true` (default `false`) **and** the call arrived over stdio (`CallerContext.transport === "stdio"`); an HTTP call, or any caller that does not set a transport, is refused regardless of the flag, because the launch would happen on the server host. The launcher spawns `xdg-open` (Linux), `/usr/bin/open` (macOS) or `rundll32.exe url.dll,FileProtocolHandler` by absolute path (Windows) with an argv array and `shell: false` (never `cmd /c start`), `stdio: "ignore"` and a 5 second timeout. The URI is rebuilt by `buildObsidianUri("open")` from the vault-relative path, percent-encoded, then validated against `obsidian://open?vault=...&file=...` (scheme exactly `obsidian`, exactly those two parameters, every character an unreserved mark or a well-formed `%XX`); no caller-supplied URI is accepted. When neither path is available the tool returns `available: false` with a `reason` and a `hint`.

### `*_active_file` governance

`get_active_file`, `update_active_file`, `append_active_file`, `patch_active_file` and `delete_active_file` take no path: the target is the note open in the live Obsidian session, resolved once per call through the companion's `GET /files/active`. They declare the scopes of the tools they delegate to (`read:notes`, `write:notes`, `delete:notes`; `delete_active_file` is `destructive`) and `pathAcl` on the resolved path, and they run the registered `read_note` / `write_note` / `append_note` / `patch_note` / `delete_note` handlers, so the per-vault folder ACL, memoryDefense, snapshots, compare-and-swap and the `write_note` overwrite confirmation apply as for a path-addressed call.

The resolution is a dispatch stage (`ToolDefinition.resolveTarget`) that runs after the authentication, scope, vault-binding, read-only and vault-kind gates, so a caller those refuse never probes the live session, and before precheck, idempotency and confirmation. The resolved path is merged into the validated input and folded into the args hash, so the confirmation's `args_hash`, the `replay_drift` fingerprint, the idempotency claim and the audit row all name the note actually hit: a confirmation raised while note A was open is not redeemable after focus moves to note B. The folder ACL is checked on the resolved path at that stage, before any confirmation is raised, and a denial carries no `path` (the caller did not name it). No active file, no live session or an old companion is a typed error with a hint; there is no default-path fallback. A non-markdown active file (canvas, PDF, image) is refused for update, append, patch and delete, and `get_active_file` returns metadata only for it.

### `execute_command` governance

Default mode `production`: tool returns `execute_command_disabled` regardless of token scopes.

Development mode:

```yaml
execute_command:
  mode: development
  allowlist:
    - "git status"
    - "git log --oneline -10"
    - "ls"
  hitl: always_elicit          # floor; cannot lower
```

Each allowlist entry is exact-match on command + args. No globs.

Hardcoded denylist applied first regardless of allowlist (shell-metacharacter denial): `rm`, `mkfs`, `dd`, `>`, `|`, `;`, `&&`, `||`, `$(`, backtick. Presence of any denylist token in the input string → refuse.

Refusal taxonomy:

| Code                         | Cause                                                                      |
| ---------------------------- | -------------------------------------------------------------------------- |
| `execute_command_disabled`   | Mode is `production`.                                                      |
| `command_not_allowlisted`    | Mode is `development` but command is not in the operator allowlist.        |
| `command_unsafe`             | Command contains a hardcoded-denylist token.                               |

### Rate limits

Token bucket per `(caller_hash, scope_class, vault_id)`. Bucket state lives in a pluggable backend, `throttle.backend`: `memory` (default; process-local, restart resets buckets), `sqlite` (shared by every process on one host through the cacheDir) or `redis` (shared across instances). See the docs page "Rate-limit backends" for configuration and the failure policy.

Tiered defaults:

| Scope class | Rate       | Burst |
| ----------- | ---------- | ----- |
| `read:*`    | 600 / min  | 100   |
| `write:*`   | 60 / min   | 20    |
| `bulk:*`    | 10 / min   | 3     |
| `execute:*` | 5 / min    | 1     |
| `admin:*`   | 5 / min    | 1     |

Backoff signaling: MCP error response includes `retry_after_seconds`. OTEL span attribute `rate_limit.hit: true`. Prometheus counter `obsidian_tc_rate_limit_hits_total{vault, scope_class}` increments.

Refusal: `rate_limit_exceeded` with `details: { scope_class, retry_after_seconds, current_burst, current_rate }`.

Multi-process and multi-instance rate limiting shipped in V1.x as the `sqlite` and `redis` backends (status: shipped). When a shared backend is unreachable, `throttle.failurePolicy` decides: `fail-open` (default) keeps serving on per-process local buckets, `fail-closed` refuses the call as `throttled` with `details.reason: "backend_unavailable"`. The limiter runs after authentication, scope and ACL checks, so it bounds authorized calls rather than guarding an access boundary; that is why `fail-open` is the default.

## Operational notes

- Signing key file mode 0600 enforced at startup. Server refuses to start if mode is more permissive.
- All security-relevant events emit MORGIANA events (`tc.acl.denied`, `tc.elicit.*`, `tc.rate_limit.hit`). See `docs/G2.4-observability.md`.
- No telemetry leaves the host unless explicitly configured (OTEL endpoint, Prometheus scrape from a remote, MORGIANA HTTP push).
- `obsidian-tc auth list` (CLI) shows issued token JTIs with `kid`, `sub`, `exp` and state (`active`, `revoked`, `expired`); `--keys` lists signing keys instead. It never prints a token or key material. Useful for forensics after a suspected compromise.
- `obsidian-tc auth revoke <jti>` revokes a single token; `auth rotate-key` revokes everything a key signed.

## CLI surface

```
obsidian-tc token mint <flags>        # mint a JWT (records its jti + kid); there is no `auth init`/`auth issue`
obsidian-tc auth rotate-key [--grace <seconds>]   # new active key; old one retires after the grace (default: at once)
obsidian-tc auth list [--all] [--keys] [--json]   # issued JTIs (not expired; --all adds expired), or signing keys
obsidian-tc auth revoke <jti> [--reason <text>]   # revoke one token before its exp
```
